---
name: git-commit
description: Use when the user wants to commit, push, or land a branch — merge it into the default branch and clean it up — invoked as /git-commit. Summarizes the working tree (staged or unstaged) into one or more English commit messages, then asks via multiple choice whether to make a single commit or a sensible split, whether to also push, and, off the default branch, whether to merge the branch in and delete it. Pull requests are NOT part of the default flow — gh is never consulted unless the user explicitly asks to open a PR. Owns the feature/NAME branch naming scheme. Never commits, pushes, opens a PR, merges, or deletes a branch without that confirmation.

# GIT COMMIT

Guided commit: read changes, propose message(s), confirm via multiple choice, then
execute exactly what was chosen. Messages in **English**. Never commit or push
before the user picks an action.

# THE PR TRIGGER — off unless the user asks
**PRs are not part of this flow by default.** No `gh` probe, no PR option in STEP 3, no STEP 6 — unless
the user asked for a PR. Opening one is outward-facing and not cleanly reversible (HARD RULES), so it
does not belong among two otherwise local choices.

**Triggered by** an imperative request from the user meaning "open a PR", in the invoking message or
earlier in the same conversation: "erstell nen pr" (the canonical example), "open a PR", "make a PR",
"PR erstellen". Read it as INTENT, not as a literal string — the user should not have to remember magic
words in one language.

**NOT a trigger**, none of these:
- a NEGATED or hypothetical mention — "no PR for this one", "not ready for a PR", "what would the PR
  say". Each contains the token and asks for the opposite. The trigger is the REQUEST, never the word.
- `gh` being installed · a GitHub-hosted remote · sitting on a feature branch
- a previous run in this session having opened one.

Not triggered → skip everything marked *(PR path)* below. Triggered → those parts switch on, and the
Step 3 confirmation still governs: the trigger authorizes OFFERING a PR, never opening one.

# STEP 1 — INSPECT
Gather staged AND unstaged before proposing:
- `git status --porcelain=v1 -b` — branch, ahead/behind, every changed path.
- `git diff` — unstaged.
- `git diff --staged` — staged.
- `git rev-parse -q --verify MERGE_HEAD` — merge in progress? A merge whose conflicts are ALL resolved shows no `U` codes in status; it exists only here. Status alone cannot see it.
- `git remote` — the remote NAMES → `<remote>`. `origin` is a convention, not a guarantee; every command below uses the resolved name, never a hardcoded `origin`. Several → prefer `origin` if present, else ask which.
- *(PR path only — skip entirely when the trigger did not fire)* `gh --version` + `git remote get-url <remote>` — CAN a PR be opened? Needs BOTH `gh` AND a GitHub-hosted remote: STEP 4 opens PRs only via `gh pr create`. GitLab/Bitbucket → no mechanism here, so Step 3 withholds the option rather than offering what STEP 4 can't run. Status shows none of this. Probe fails → re-check in the OTHER available shell before concluding absence: a tool can sit on the OS PATH yet miss a POSIX shim's, and a false negative silently strips the PR option. Not triggered → this probe never runs, and nothing below needs its answer.
- **`<default>`, the default branch's NAME — only when a remote exists** (no remote → skip this, see below). In order: `git symbolic-ref --quiet --short refs/remotes/<remote>/HEAD` (strip `<remote>/`) → else ask. **Never assume main/master** (a repo may use `develop`/`trunk`) and **never use `init.defaultBranch`** — it describes what NEW repos get, not what THIS repo has, and is routinely stale. **"Couldn't resolve" is NOT "not the default"** — that would silently disable Q0 and the never-commit-to-the-default rule. Only the first step is free: `refs/remotes/<remote>/HEAD` is set by `git clone`, NOT by `git init` + `git remote add`, so a non-empty `git remote` does not imply it exists. **Resolve it AFTER the STOPs below have all passed**, not here in gather order — its only consumers are Q0, Q3 and the push-only exception, none of which a stopped run reaches, and its fallback is a question to the user. Asking someone to name their default branch and then telling them the tree is clean and nothing will happen is a question spent on a run that does nothing.
  `gh` is not consulted for anything unless the PR trigger fired, so there is no third source between those two. **Asking here is normal, not a defect** — in a repo made by `git init` + `git remote add` it will happen every run. Answer it; **never "fix" the friction by hardcoding `main`**, which the rule above forbids in bold and which is the exact shortcut this note exists to head off.
- **No remote at all** → no shared default branch exists to protect: skip `<default>`, Q0 is not required, and Q2 offers no push (nor a PR, on the PR path). Stated as a decision, not left to fall out: a local-only repo has no one to disrupt by committing on its main branch.
- Untracked files → note them (need `git add`).

Clean = nothing staged, nothing unstaged, AND nothing untracked. Untracked-only is NOT clean — those are the commit. Clean → say so and STOP; don't create an empty commit. **Except the PUSH-ONLY EXCEPTION at the end of this step — read it before you stop.** A clean tree can still have unpushed commits, and this flow owns pushing too. That jump does NOT skip anything between here and there: the two STOPs immediately below still bind, and so does the record-keeping paragraph after them — the push-only path still offers Q3, and Q3 reads its ahead-of-`<default>` input from exactly that paragraph. Evaluate all of it in order; the exception is the LAST thing this step decides.
Unmerged paths (`U` codes in status) OR a merge in progress (`MERGE_HEAD` exists) → surface and STOP. Both, not either: a fully-resolved merge is invisible to status yet is exactly the state where committing concludes the merge silently. This skill commits; it does not resolve merges.
Detached HEAD (`## HEAD (no branch)`) → surface and STOP. This flow is branch-keyed throughout — Q0, push, and a PR where one was asked for, all assume one; commits made here are unreachable once you move away.
Record the current branch and — when a `<default>` was resolved — whether it IS that default. Compare against the resolved name, never against the literals main/master. Record two more things, both needed by Q3: whether the branch has an UPSTREAM — for REPORTING only; the remote delete re-reads it live at STEP 4's land step 2, because a push in this same run can create one and this record would then be stale — and whether it is AHEAD of `<default>` — **`git rev-list --count <default>..HEAD`, a non-zero count means ahead** (nothing ahead → nothing to merge → Q3 is not offered; say why, or a user looking at `[ahead 1]` on the status line sees a question silently missing). That command is stated because nothing else here produces the value: `git status -b` reports against the upstream only, and an executor with no command invents one. **Run it only when `<default>` actually resolved**, and never read its failure as an answer: with no remote there is no `<default>` to compare against and the command errors, which is not "not ahead" — same rule as "Couldn't resolve" is NOT "not the default" above. Unresolved → Q3 has no input and is not offered; say why. And a THIRD, needed by the push-only exception below and by Q2: whether the branch is AHEAD OF ITS UPSTREAM. That is a DIFFERENT comparison from ahead-of-`<default>` and the two are routinely both recorded and then conflated: a feature branch already merged into `<default>` locally is ahead of neither, while `<default>` itself with local commits is ahead of its upstream and ahead of nothing else.

Hygiene scan: flag obvious secrets (`.env`, key/token/credential files), large binaries, and build/generated artifacts among the changes. Don't stage them — surface them to the user and suggest a `.gitignore` entry instead. Never blind-stage them via `git add -A`.
**Scan excluded at least ONE path, and nothing survived it → surface them, suggest the `.gitignore` entries, and STOP.** Both halves are required. Over an EMPTY change set "every path was excluded" is vacuously true, so a one-half reading STOPs on a clean tree and the push-only exception below is never reached at all. Nothing is left to commit, and without this exit the run continues: the tree is not "clean" by the definition above (untracked-only is not clean), so no STOP fires, STEP 2 proposes a commit over an empty path set, STEP 3 asks how to make it, and STEP 4 reaches `git commit` with an empty index. "Don't stage them ... instead" is the intent; this sentence is what executes it. **Narrow on purpose:** it fires only when the scan excluded ALL of them. One `.env` beside real changes is the ordinary case — exclude the `.env`, commit the rest. Two consequences to state rather than let the reader discover: the excluded file stays in the tree, so **Q3's landing cannot run this session** (land step 1 STOPs on it) — Q3's description says so; and when this STOP fires on a branch that is also AHEAD of its upstream, those commits are still unpushed. The push-only exception cannot reach them, because it needs a clean tree and an untracked file is not clean. Say the count and tell the user a push is available once the file is ignored or removed. A STOP that silently swallows unpushed work is the defect this whole exit was written against.

**PUSH-ONLY EXCEPTION — the one case where a clean tree does not end the run.** Clean AND a remote exists AND the branch has commits the remote does not → do NOT stop. Skip STEP 2 (there is nothing to analyze or propose) and go to STEP 3, which asks about pushing only. Read the state off `git status --porcelain=v1 -b`'s branch line. Both forms below CAN be pushable, and each carries its own disqualifier — read the bullet to its end before offering anything:
- `## <branch>...<remote>/<branch> [ahead N]` — has an upstream, N commits unpushed. `git push`.
- `## <branch>` with no `...<remote>/<branch>` part at all — no upstream, so THIS BRANCH does not exist on the remote. Not the same as "none of its commits are pushed": a branch cut from an already-pushed `<default>` shares every one of those commits. What a push publishes here is the branch itself plus whatever it added. Added nothing → the exception's own condition at the top ("commits the remote does not") is FALSE and this STOPs like any other clean tree; say so rather than offering to publish a duplicate of `<default>`. **Compute it: `git rev-list --count HEAD --not --remotes=<remote>`** — commits no remote branch has; non-zero means pushable. It needs no `<default>`, so it also works where that name is not bound. **The argument order is load-bearing:** `--not` inverts every ref that FOLLOWS it, so `--not --remotes=<remote> HEAD` excludes HEAD as well and reports 0 on a branch that has unpushed commits. Measured 20260803: 0 from the inverted form where the correct one gave 1. There is no `[ahead]` marker to find here: a condition written to look for one reads FALSE on every never-pushed branch, which is exactly what a `feature` or `crew` run leaves behind. `git push -u` is the form (STEP 4). **This line shape alone is NOT enough** — a repo with no remote at all prints the identical `## <branch>`, so `git remote` decides between them and must be read. Verified 20260803: a never-pushed branch and a remote-less repo were indistinguishable by branch line and separable only by `git remote`.

Everything else on a clean tree still STOPs as above: `## <branch>...<remote>/<branch>` with no `[ahead N]` (nothing unpushed, `[behind N]` alone included — this flow does not pull), and no remote at all (nothing to push TO, and STEP 3 has no push option to offer). Detached HEAD and a merge in progress (`MERGE_HEAD`, resolved or not) already STOPped above and never reach here — a clean tree does NOT clear `MERGE_HEAD`, so that STOP is not redundant with this one and the exception never overrides it.
This exception creates no commit OF ITS OWN. The empty-commit prohibition stands untouched; what it gains is a path for commits that already exist. A merge commit can still appear downstream when Q3 lands the branch — that is Q3's doing, confirmed by Q3, not this exception quietly committing.

# STEP 2 — ANALYZE & PROPOSE
Prepare BOTH options:
1. **Single commit** — one message, when changes are one cohesive unit.
2. **Split into N commits** — group changed files by concern (feature vs fix vs docs vs config, or by module). Each group = its own `{files, message}`. Split only along real seams; never invent artificial splits. Concerns interleaved WITHIN one file (i18n bundle, shared doc/config) can't be file-split — surface it and offer a combined commit, or STOP so the USER stages the hunks themselves. Only SOME files interleaved → a third option beats both: isolate the clean groups into their own commits and confine the mixing to ONE. Name which commit is mixed and why. Never patch-stage: this flow has no non-interactive way to do it (`git add -p` needs a terminal you don't have), so offering it would promise what STEP 4 can't execute. Never silently sweep one concern into another's commit.
**Then ORDER the groups so every commit builds.** Group B referencing what group A adds — an import, a script entry, a new file — lands after A. Check the direction before proposing an order: a split that reads right by concern can still leave a commit that does not compile, and that breaks bisect and CI on a commit nobody ever ran. Concern decides the GROUPS, dependency decides their ORDER.

Message format (English, Conventional-Commits-friendly, not mandatory):
- Imperative subject ≤ ~72 chars, no trailing period.
- Optional body (blank line, wrapped) when the "why" isn't obvious.
- No `Co-Authored-By:` / "Generated with Claude" line — see HARD RULES.

# STEP 3 — CONFIRM via AskUserQuestion (REQUIRED — see APPROVAL GATES, end of file)
**Arrived via STEP 1's PUSH-ONLY EXCEPTION?** Then this step asks about pushing only — on ANY branch, `<default>` included. Read this block first; everything after it assumes there is something to commit.
- **Q0 is not asked.** Its only job is offering to branch BEFORE committing on `<default>` (HARD RULES). There is no commit to make, and switching branches now cannot move commits that already sit on `<default>`.
- **Q1 is not asked.** SUPPRESSED, not asked with an empty option set — a commit question with nothing to commit is an invitation to make the empty commit STEP 1 forbids.
- **Q2 loses its commit half.** Options "Push" / "Don't push". Its heading needs no special handling on this path: the rule below already replaces every `Qn — ` heading with a plain question, and Q2's is "Push?" on every path. A remote is guaranteed here (STEP 1's exception requires one), so the push option always exists. *(PR path only)* triggered → a third option "Push and open a PR"; it needs a branch ≠ `<default>`, and Q0 is not in this round to create one, so on `<default>` it is simply not offered and the Q0 × Q2 contradiction below cannot arise. That option also has no Q1 to build a PR title from — STEP 4's `<title>` rule covers it.
- **Q3 keeps every precondition below — feature suppression included — but loses its commit half too.** Its options here read "Keep the branch" / "Merge into `<default>` and delete the branch — here AND on `<remote>` if it is published there" — the same remote clause the labels below carry, and dropped the same way, only when no remote exists at all. The labels written below both begin with "Commit"; asked unchanged on this path they promise a commit this run cannot make, which is the same defect Q1's suppression exists to prevent.

**The `Qn — ` prefixes and the parentheticals below are AUTHORING labels, not user-facing text.** "(default branch only)" and "(off the default branch only)" are the conditions under which a question is asked; a user is never on both sides of them and shipping the parenthetical is spec leaking into the UI. Show the plain question: Q0 → "Commit on `<default>`, or branch first?" · Q1 → "How to commit?" · Q2 → "Push?" · Q3 → "Land the branch?". Refer to them as Q0..Q3 in this file and among yourselves; never to the user.

On the **default branch** (the name Step 1 resolved — not the literal main/master) → Q0 is REQUIRED, asked alongside Q1/Q2, never folded into Q2 as an afterthought:

**Q0 — Branch (default branch only):**
- "Commit directly on `<default>`" / "Create a new branch first".

**Q1 — How to commit:**
- "Single commit" (include the proposed subject).
- "Split into N commits" (summarize groups + subjects).
- Trivial/one-concern tree → put "Single commit" first as recommended.

**Q2 — Commit only, or also push:**
- "Just commit" / "Commit and push". **Two options. No PR option** — that is THE PR TRIGGER's doing, at the top of this file.
- *(PR path only)* Triggered → a third option is added, "Commit, push and open a PR", and the two paragraphs below switch on with it.
- *(PR path only)* The PR option needs a branch ≠ default. On the default branch that means Q0 must be "Create a new branch first" — but Q0 and Q2 are asked in the SAME round, so Q0's answer doesn't exist yet when Q2's options are built. The contradictory pair (Q0's commit-on-`<default>` option + Q2's PR option) is therefore selectable, and must be handled, not assumed away: it arrives → surface the conflict and re-ask Q0 + Q2 only (Q1's answer stands; don't re-ask it). Never silently override either answer to resolve it — an overridden answer is not a confirmation. Same contradictory pair chosen again → stop and report; don't loop.
- No remote → do not offer "Commit and push": `git push` cannot succeed. *(PR path only)* a PR also needs a pushed branch, so it goes too; remote present but no `gh`, or the remote is not GitHub-hosted → drop the PR option only. Say why in every case.
- **Options are referred to by ROLE here — "Q2's PR option", "Q0's commit-on-`<default>` option" — never by their literal label.** This section and the Q3 one below are exercised only on the rare PR path, and a paragraph quoting a label that some later edit reworded describes a trap its reader will not recognise.

**Q3 — Land the branch (off the default branch only):**
- Offered only when ALL hold: current branch ≠ `<default>`, the branch is AHEAD of `<default>` (Step 1 recorded both), and NO feature owns it. `feature` step 7 asks instead — it is the single owner of a feature branch's landing. Suppressed here, and say why: asked in both places, one branch collects two different answers, and intermediate commits during `feature` step 5 would offer to land unfinished work every time.
- **Ownership does NOT expire at DONE.** A feature owns its branch until step 7 is FINISHED with it — its branch question asked AND the answer executed — and step 7 moves the file to `done/` BEFORE invoking this skill, so "that feature is DONE" reads TRUE at exactly the moment Q3 must stay quiet. `done/` therefore proves nothing in either direction; a NON-terminal folder proves ownership. That asymmetry is the whole on-disk test — it is not "which folder" in the sense of trusting the folder to mean finished.
- **How to decide it, in this order — and it FAILS CLOSED.** Any step below that cannot reach an answer suppresses Q3 rather than offering it. The two wrong guesses do not cost the same: guess "owned" and one run is missing a question the user can ask for again; guess "not owned" and one branch collects two landing answers and a remote branch is deleted under an authorization nobody gave.
  1. **Was this run invoked BY `feature` step 7?** That is context, not a command — it is who called you, and nothing on disk records it. Yes → step 7 owns the landing; Q3 stays suppressed. **Cannot tell → treat as yes and suppress.** A `/git-commit` the user typed in front of you is the only reliable no.
  2. Otherwise search for a feature file whose slug matches this branch. Root: `$(git rev-parse --show-toplevel)/features`. The branch scheme is `feature/<slug>` and feature ids are `YYYYMMDD-HHMM-<slug>.md`, so match `????????-????-<slug>.md` — **not** `*-<slug>.md`, which also matches a longer slug ending in yours and would suppress a legitimate Q3 silently. Search `draft/ pending/ approved/ in-progress/ ready-for-done/` only. **Hit → that feature owns the branch: suppress Q3 and name the file. Clean miss with the directory PRESENT → nobody owns it; Q3 may be offered.** Branch not of the form `feature/<slug>` → there is no slug to match; treat it as a clean miss.
  3. **An ABSENT `features/` is not a clean miss.** It is routinely VCS-ignored, so a LINKED WORKTREE does not have it even when the project does — and a linked worktree is exactly where delegated workers run. Test which you are in: `git rev-parse --path-format=absolute --git-dir --git-common-dir` prints two paths — identical in the main worktree, different in a linked one. **`--path-format=absolute` is not optional.** Without it the two come back in different FORMS from a subdirectory and a plain string compare reports "linked" in the main worktree — measured 20260803 from `skills/`: `--git-dir` gave `D:/Projects/claude-config/.git` while `--git-common-dir` gave `../.git`. A drifted shell would then suppress Q3 for no reason. Linked → you cannot see the answer from here; suppress Q3 and say why. Main worktree and still no `features/` → the project does not use the feature workflow; nobody owns it, and that is an ordinary answer rather than a failed check.
- "Just commit, keep the branch" / "Commit, then merge into `<default>` and delete the branch — here AND on `<remote>` if it is published there".
- **The hygiene scan excluded a path → say HERE that landing cannot happen this run.** Land step 1 STOPs on anything left in the tree, and an excluded `.env` is left in the tree. Offering the option and letting it die inside the sequence wastes the user's answer; say it in the option's description and let them ignore the file first.
- **The label NAMES the remote delete because Q3's yes is what authorizes it.** STEP 4's land list pushes a deletion; nothing else in this flow asks about it. Leave it unnamed and the user authorizes a remote mutation they were never shown.
- **Do NOT strip that clause off a never-pushed branch just because Step 1 saw no upstream.** Q2 and Q3 go out in the SAME round, so Q2's push can publish the branch before the land list runs, and the delete then fires on an upstream Step 1 never saw — the label hiding exactly the mutation the bullet above exists to show. Word it "and on `<remote>` if it is published there"; land step 2 reads the truth, and it reads it after Q2 has been answered. The clause drops only when NO remote exists at all: nothing can be published, so promising a remote delete is the mirror defect.
- **The label carries the ACTION; the option's description carries why it is safe.** Say there that the branch is merged by the time it is deleted, and that `git branch -d` refuses — and stops the list — if it is not. A label that reads as dangerous gets declined, branches then accumulate, and a correct action nobody takes is not an improvement on a silent one.
- Q0 and Q3 can never both apply: Q0 exists only ON the default branch, Q3 only off it.
- *(PR path only)* **Q2 × Q3 is the same trap as Q0 × Q2, for the same reason.** Every question goes out in ONE round, so Q3's options are built before Q2's answer exists, and the pair (Q2's PR option + Q3's merge-and-delete option) IS selectable. Handle it, don't assume it away: it arrives → surface the conflict and re-ask Q2 + Q3 only (Q1's answer stands — or, on a push-only run, Q1 was never asked and there is nothing of its to preserve). Same pair again → stop and report. Never override an answer to resolve it, and never let the merge delete a branch `gh pr create` is about to use as its head. Not triggered → Q2 has no PR option, so this pair cannot arise.

Don't proceed until all applicable questions are answered. "Other"/cancel → do nothing, report it.

# STEP 4 — EXECUTE
- **New branch first** (if chosen): `git switch -c feature/<kebab-name>` from the change summary. The `feature/` prefix is the scheme for EVERY branch this config creates — inside a `feature` run the slug is the feature file's own, timestamp dropped. Slug already starts with the prefix → don't double it (`feature/x`, never `feature/feature-x`). This step owns the scheme; `feature` step 5 and `crew` step 4 point here.
- **Single commit:** stage intended paths (`git add -- <paths>`; `git add -A` ONLY after the Step 1 hygiene scan ran and found nothing to exclude), then `git commit -m "<subject>" -m "<body>"` (no co-author footer).
- **Split:** per group in order — `git add -- <that group's paths>` then **`git commit -m "<subject>" -m "<body>" -- <that group's paths>`** — message flags kept, pathspec repeated on the commit. The `-m` is not optional: without it git opens `core.editor`, and a captured subprocess has no one to answer it. Keep groups disjoint. The pathspec is what actually leaves already-staged-but-unrelated changes for their own group: a bare `git commit` writes the WHOLE index, so anything the user staged before this run is swept into group 1 and group 2 then has nothing left to stage. Verified 20260803: with `b.txt` pre-staged, bare `git commit` produced a group-1 commit containing `a.txt` and `b.txt`; `git commit -- a.txt` produced one containing `a.txt` alone, with `b.txt` still staged.
- **Push** (if chosen): `git push`; no upstream → `git push -u <remote> HEAD` (Step 1's resolved remote name, not a hardcoded `origin`).
- **Open PR** *(PR path only; if chosen)*: only after the push succeeded — `gh pr create --base <base> --head <head> --title "<title>" --body "<STEP 6 body>"`. Never `--fill`: it reuses the commit message and silently skips STEP 6. Push failed → STOP and report; never simulate an opened PR. (Untriggered runs never reach here at all — Q2 has no PR option. Triggered but no remote / no `gh` / non-GitHub remote also cannot: Step 1's probe detects all three and Step 3 withholds the option.)
  - `<base>` — the default-branch name Step 1 resolved. Never assume `main`.
  - `<head>` — re-read it HERE: `git branch --show-current`. Never reuse Step 1's record: Step 1 ran before this step's `git switch -c`, so on the Q0="new branch" + PR path its value is the default branch — the one you're forbidden to open from.
  - `<title>` — Q1 "Single commit" → the commit subject. Q1 "Split into N commits" → a subject describing the branch as a whole; there are N subjects and none of them is the PR's. **Q1 was SUPPRESSED (push-only run)** → same as the split case: write a subject describing the branch as a whole, from the commits the PR will CONTAIN (`<base>..<head>`) — NOT from the ones being pushed. Those two sets differ on any branch already partly pushed, and they are precisely the ahead-of-`<default>` vs ahead-of-upstream pair Step 1 warns about. There is no commit subject to reuse and `--fill` stays forbidden, so this branch must be stated rather than left to fall through the two above.
- **Land the branch** (if Q3 chose it — or if `feature` step 7's own branch ask chose it and sent its executor straight here; that ask REPLACES Q3 on a feature-owned branch, which is why Q3 stays suppressed there, and this list is the procedure for both): runs LAST and runs ONCE — after EVERY commit of the split, and after the PR bullet ABOVE. Never inside the per-group loop. The reason it sits at the end rather than carrying a warning is structural: a split leaves groups 2..N unstaged while group 1 commits, and a merge in the middle carries them across the `git switch` onto `<default>`. It sits after the PR bullet for defence in depth only — Q3's merge-and-delete and Q2's PR option are a forbidden pair that the Q2 × Q3 paragraph in STEP 3 re-asks and then refuses, so a run reaching BOTH bullets should not exist. Do not read this order as a recipe for running them together; if you ever find yourself here with a PR open on this branch, stop and report instead. Then, in order:
  1. Tree must be clean — **STEP 1's definition, all three parts: nothing staged, nothing unstaged, nothing untracked.** Anything left → STOP; never merge on top of it. Staged belongs in that list as much as the other two: a split that ended early leaves group N's paths staged, and `git switch` carries them onto `<default>` exactly like unstaged ones. **A path the hygiene scan excluded is still "left".** A run that set a `.env` aside and committed the rest therefore cannot land in that same run — see the note under Q3, which is where the user must be told, not here.
  2. **Read the branch's upstream NOW, before anything is deleted** — `git rev-parse --abbrev-ref <branch>@{upstream}` (or ask the remote: `git ls-remote --heads <remote> <branch>`). NOT Step 1's record: the push bullet above may have created the upstream in this same run via `git push -u`, so Step 1's "no upstream" is stale by the time you stand here. And not later either — step 6 needs this value, and by then step 5 has deleted the branch and its config with it. This is the one moment both facts are available. Same guard as `<head>` in the PR bullet, same reason, moved to where it can actually execute.
  3. `git switch <default>` — the name Step 1 resolved, never the literal `main`. **Check the exit code; a failure here must never fall through to the merge.** Inside a LINKED worktree this fails when `<default>` is checked out in another one — exit 128, `fatal: '<default>' is already used by worktree at '<path>'`, measured 20260803. Any non-zero → report and STOP. Nothing below has run, so there is nothing to undo; merging while still standing on `<branch>` is exactly what this check prevents.
  4. `git merge --no-ff <branch>` — always a merge commit, so the branch stays visible in history. Conflict → `git merge --abort`, report, STOP. **Any other non-zero exit** — unrelated histories, a rejected hook, signature verification — → report and STOP as well; never fall through to the delete. Check the exit code, do not scan the output for the word "conflict". Resolving any of it is not this skill's job, and a half-merged tree blocks every later run of this flow (Step 1 STOPs on `MERGE_HEAD`).
  5. `git branch -d <branch>` — lower-case `-d`, never `-D`. It refuses, and that refusal is the signal to stop: report it, delete nothing, **and STOP the list here** — do not run 6 or 7. **Exit 1 is not one cause.** Measured 20260803, three share it: `the branch 'X' is not fully merged`, `cannot delete branch 'X' used by worktree at '<path>'`, and `branch 'X' not found`. The exit code cannot tell them apart, so NAME the cause from commands before reporting one, in this order. `git rev-parse --verify --quiet refs/heads/<branch>` prints nothing and exits non-zero when there is NO SUCH BRANCH — check that first, because the next command is empty for that case too and would read as "unmerged". It exists → `git branch --merged <default> --list <branch>` is EMPTY when the branch is genuinely unmerged, and prints a `+`-prefixed line when it is merged but checked out in another worktree. Assert the wrong cause and the user goes off to fix what is not broken — or, on a branch that does not exist, gets told to switch back to it. The STOP is IN this list on purpose: "delete nothing" as prose above a numbered list does not stop the numbered list, and step 6 would delete the REMOTE copy of the branch whose local delete just refused — the sole surviving copy of unmerged work. Stopping here leaves you on `<default>`, and what to say next depends on the cause you just named. UNMERGED → the work is still on `<branch>`; say both and name it, so the user can switch back. The other two → the merge already landed, nothing is stranded, and on the worktree cause `git switch <branch>` is refused anyway (exit 128, another worktree holds it). Never offer a switch-back that git will reject.
  6. Step 2 found an upstream → `git push <remote> --delete <branch>`. Found none → nothing remote to delete; say so. Fails (already gone, no permission) → the local delete stands; report the failure, never force.
     **The merge is staying local → do not delete the remote branch either.** Both or neither, and this is the branch where that invariant is easiest to lose: step 7 below leaves the merge local, and deleting the published branch on top of that empties the remote of the work with nothing published in its place. Keep the branch, say it was kept, and say why — the landing still happened locally. **Decide it off ONE thing: does the answer that AUTHORIZED this landing NAME the `<default>` push?** Q3's label does not, so on a Q3 landing that push rides on Q2 and Q2 alone: Q2's commit-only option leaves the merge local and this bullet FIRES, exactly as before; Q2's push option publishes it and this bullet does not. `feature` step 7's branch ask DOES name it, so a landing it authorized deletes the remote branch on ALL THREE of that step's paths, including the two that ask a Q2 and may have taken its commit-only answer. **Not narrower than that, and this is why**: Q2 decides whether to push the BRANCH, and on no path is it asked whether to publish the LANDING — so it cannot be read as refusing one, and re-narrowing this to "no Q2 exists in this run" discards the user's explicit "and push `<default>`" on two paths out of three. **Never key it on who CALLED you.** That is the one fact Q3's decision procedure records as not being on disk — and Q3 fails CLOSED on it by suppressing itself, where this bullet would fail OPEN, deleting a remote branch exactly when the executor cannot tell. **Cannot tell which answer authorized this landing → this bullet APPLIES; delete nothing remote.**
  7. `<default>` is pushed only if Q2 chose push — `git push`, or `git push -u <remote> HEAD` when `<default>` itself has no upstream. Otherwise the merge stays local and STEP 5 says so. Never push it unasked. **Reached from `feature` step 7's branch ask** — on ANY of that step's three paths, whether or not this skill also asked a Q2 — → that ask governs instead, and its yes covers this push. That is not overriding Q2: Q2 decides the BRANCH push and is never asked whether to publish the LANDING, so it has nothing to say here. It is reading the answer that authorized step 6, which came from the other file. It must cover both or neither — but the pairing is ASYMMETRIC, and this is where reading it as symmetric goes wrong. What it forbids is a remote delete with the merge left local: that empties the remote of the work the feature just finished. A push with nothing to delete is harmless. So: **Q3 landing** → step 6 ran → push `<default>`; step 6 did not → leave it local. On that path it is an identity with Q2, which decides both. **`feature` step 7 landing** → step 6's OUTCOME does not decide it: push `<default>` whether or not there was a remote branch to delete. A never-published branch is what a `feature` run ordinarily leaves behind, step 6 then has nothing to delete and says so, and keying the push on that would refuse the exact half the user's answer named. What DOES decide it is that ask's own wording, which is why the carve-out above says its yes COVERS this push — no remote at all and the ask dropped its push clause, so there is nothing to push and the `<default>`-binding paragraph below governs instead.
  **`<default>` must be BOUND before step 3 — CHECK it here, never re-resolve it.** Both entries bind it upstream of this list: via Q3, which needs the ahead-of-`<default>` count to be offered at all; via `feature` step 7, which binds it to word its own landing question. Bound → carry on. Not bound → resolve by STEP 1's `<default>` recipe now, and never by moving that recipe back into gather order. The check is not ceremony: STEP 1's fallback is a QUESTION, so an executor that re-resolves unconditionally asks the user to name their default branch twice in one landing. `feature` step 5 bans hand-rolling the name so this file stays its only source. No remote → STEP 1 skipped the name by design, not for lack of one: a local-only repo has a default branch and merges into it fine. Ask the user for it and carry on; steps 6 and 7 then have nothing remote to do and say so.

Multi-line messages → here-doc / multiple `-m`. Quote paths. **The subject is ONE physical line, and a blank line follows it.** Wrap the first line and git FOLDS the continuation into the subject rather than reading it as body — so the ≤ ~72-char rule above ships a 100+ char subject with a doubled space at the seam, and nothing warns.

# STEP 5 — REPORT
State exactly what happened: each commit's short hash + subject, the branch you ENDED on (Step 4 may have switched — don't report Step 1's record), whether pushed (+ where), and the PR URL if one was opened.
**Push-only run** (STEP 1's exception) → there are no new commits. Say that in words instead of printing an empty list, or the run reads as having done nothing: no commit was made, N already-existing commits pushed to `<remote>/<branch>`. N is STEP 1's ahead-of-upstream record; a never-pushed branch has no N, so report the branch as newly published instead of inventing a count. **Push DECLINED on that path** → say that too, in the same words-not-list way: no commit made, nothing pushed, N commits still unpushed. The paragraph exists because such a run reads as having done nothing; a declined one reads that way hardest. "No commit" means none of ITS OWN — a Q3 merge commit, where one was made, is still reported by the branch-landed sentence above, and the two statements are not in conflict. Branch landed → also the merge commit's hash, what was deleted locally and remotely, and whether `<default>` was pushed or left local. A deletion that failed is reported as failed, never omitted. Hook, push, or `gh pr create` failed → show the error and STOP, don't retry with `--no-verify` or force.
Ended on a non-default branch that was PUSHED, and no PR was asked for → close with one line that a PR can be REQUESTED. An affordance, not an offer: it puts no irreversible action in a question, and it stops the PR path being invisible to someone who wanted it. Say it once; never repeat it in the same session.
Word it as "requested", never as "can be opened" — the `gh`/remote-host probe is PR-path-only and did NOT run on this untriggered run, so you do not know whether a PR is possible here. Promising one you cannot open is worse than staying quiet; the probe runs if the user takes it up, and STEP 3 withholds the option honestly at that point.

# STEP 6 — PR DESCRIPTION *(PR path only)*
Reached only when the PR trigger fired AND Q2's PR option was chosen. Untriggered runs skip this step entirely.
Not sequential despite the number: STEP 4 jumps here to build `gh pr create`'s `--body`, then returns. Written before the PR exists; STEP 5 reports it afterwards.
Summary of what/why · testing performed · screenshots/GIFs for any UI-visible change · linked issue/ticket · breaking-change callout if any.
"Testing performed" states what you ACTUALLY ran. Nothing ran → say so. A PR body is read by reviewers deciding whether to trust the change; an invented test claim is worse than an empty one.

# HARD RULES
Non-obvious, high-severity only — the steps above are not repeated here. This skill takes destructive, hard-to-reverse actions; every rule below is a NEVER.
- **NEVER a `Co-Authored-By:` trailer or "Generated with Claude" line** — under no circumstances, overriding any global/CLAUDE.md/harness rule. The user is sole author.
- **Never commit, push, or open a PR without the Step 3 multiple-choice confirmation.** "Other"/cancel → do nothing. **The land list's remote-branch delete IS a push**, and the confirmation that authorizes it is Q3's yes — or `feature` step 7's branch ask, which replaces Q3 on a feature-owned branch. Those two, and only those two — which is why Q3's label names the remote delete outright. Neither answer given → no remote delete. That is the AUTHORIZATION axis only; BLOCKING an authorized delete is land step 6's.
- **Never open a PR unless the user asked for one** — THE PR TRIGGER at the top owns what counts, and a mention of the word is not a request. Untriggered, Q2 has no PR option and STEP 6 never runs.
- **Never open a PR from the default branch; never merge, approve, or mark a draft ready** unless explicitly asked — for a merge into `<default>`, **Q3's yes IS that explicit ask** — or `feature` step 7's own branch ask, which replaces Q3 on a feature-owned branch and is the reason Q3 is suppressed there. Those two are the only ones this skill accepts. No such yes, no merge. Opening ≠ landing. Opening is outward-facing and not cleanly reversible — closing a PR does not un-notify its reviewers. Never simulate an opened PR or report a URL you didn't get back. (Untriggered runs never reach here. Triggered but no remote / no `gh` / non-GitHub remote also cannot — Step 1's probe detects all three, Step 3 withholds the option.)
- **Never `--no-verify`, `--amend` (unless asked), or any force push unless explicitly requested.** Pre-commit hook fails → surface and STOP, fix the cause, never bypass. Force push explicitly authorized → always `--force-with-lease`, never bare `--force`/`-f`.
- **Never commit to the default branch** without surfacing it and offering to branch first — that offer IS Q0. This governs a `git commit` you author. **The MERGE COMMIT a landing creates is carved out**, by the same yes that authorizes the merge — Q3's, or `feature` step 7's ask. Q0 cannot be that gate and never could: it exists only ON `<default>` and Q3 only off it, so demanding it here would forbid every landing this skill is built to perform. (No remote → no shared default exists to protect; Step 1 says so and Q0 is not required. Default unresolvable WITH a remote → Step 1 asks; never treat that as "not the default".)
- **Never commit obvious secrets, large binaries, or build artifacts** — see the STEP 1 hygiene scan.
- **Never commit into a merge in progress** — resolved or not; Step 1 detects both and STOPs. Resolving conflicts is not this skill's job, and committing into a fully-resolved merge concludes it silently.
- **Never `git branch -D`.** Only `-d`. Its refusal on an unmerged branch is the safety net that catches a merge which did not land; escalating past it deletes the sole copy of the work.
- **Never merge with a dirty tree, and never merge before every commit of a split has landed.** Both carry uncommitted work across the `git switch` and onto `<default>`.
- **Never delete a branch whose merge did not succeed**, and never delete one a PR still needs as its head.
